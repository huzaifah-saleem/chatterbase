# Chatterbase — Memory / Checkpoint

Running log of major work sessions, kept so a future session (human or
Claude) can pick this project back up without re-deriving context.

## 2026-09-13 — Multi-connection registries, chart type switching, dashboards

**Starting point**: a single hardcoded MCP server (`Config.MCP_SERVER_URL`)
and a single live-edited LLM provider config, both in-memory only and lost
on restart. Charts were LLM-generated but static — no way to change a
rendered chart's type, and pinning didn't exist yet.

### 1. MCP server registry (`mcp_registry.py`, `mcp_client.py`)

- Multiple MCP servers instead of one hardcoded one. Add/remove/enable via
  Settings, or bulk-import Claude-Desktop-style
  `{"mcpServers": {"name": {"url": ...}}}` JSON — url-based/remote servers
  only; `command`-based stdio servers are reported as skipped (this client
  is HTTP-only, no subprocess lifecycle management).
- Tools are aggregated across every *enabled* server. A tool name only gets
  qualified as `ServerName::toolName` when two servers actually expose the
  same bare name, so the common single-server case is byte-for-byte
  unchanged from before this existed.
- Persisted to `data/mcp_servers.json`, seeded once from `.env` on first run
  (zero manual migration for the already-running deployment).

### 2. LLM provider profiles (`llm_registry.py`)

- Named, saved connection profiles — any provider type, and multiple
  profiles of the *same* type (e.g. two different LM Studio endpoints),
  instead of one live-edited config slot per type.
- Activating a profile pushes its fields onto `Config`, so
  `llm_providers.py` / `chat_handler.py` needed **zero changes** — they
  still just read `Config.*`.
- Persisted to `data/llm_profiles.json`, seeded once from `.env`.

### 3. Chart type switching (`templates/index.html` only, no backend changes)

- Every rendered chart gets a Bar / Line / Pie / Doughnut / Radar switcher.
- Switching **destroys and recreates** the Chart.js instance rather than
  mutating `.config.type` on a live one — mutating in place left stale
  internal layout/scale state that produced broken, oversized canvases.
  Don't revert to the mutate-in-place approach.
- **Found and fixed a real pre-existing bug**: the fenced-`chart`-block
  detection regex —
  ``` /```chart\\s*([\\s\\S]*?)```/g ```
  — had string-style double-escaped backslashes inside a *regex literal*,
  where they aren't needed. `\\s` matched a literal backslash-then-`s`,
  never real whitespace, and `[\\s\\S]` matched only the literal characters
  `\`, `s`, `S` rather than "any character". Verified with a standalone
  Node snippet that this pattern **never matched real chart JSON** — charts
  generated by the LLM had never actually rendered, independent of anything
  else in this session. Fixed to ``` /```chart\s*([\s\S]*?)```/g ```.

### 4. Multiple named dashboards (`dashboard_store.py`)

- Dashboards are a first-class module now, mirroring how conversations
  already work: one file per dashboard under `data/dashboards/<id>.json`
  (not a single flat list), a Chats/Dashboards tab pair in the sidebar,
  each with its own list and its own "+ New" action.
- Pinning a chart from chat picks a target dashboard via a dropdown next to
  the Pin button (with a "+ New dashboard..." option), so charts land where
  you actually want them instead of one global bucket.
- The very first (single-dashboard) version of this feature used a flat
  `data/dashboard.json`. That gets migrated automatically into a "Default"
  dashboard the first time `dashboard_store.py` runs post-upgrade, then
  renamed to `.migrated` so the migration doesn't re-fire.
- Fixed a real UX bug: switching to a chat conversation (or "+ New Chat")
  while the dashboard view was open left the dashboard showing instead of
  switching back. `loadConversation()` and `startNewChat()` now call
  `showChat()` first.

### Two more real, pre-existing bugs found and fixed along the way

Neither was introduced by this session's work, but the dashboard/pin
feature is what exposed them:

- **`.msg-content` had no `flex-grow`**, so assistant message bubbles sized
  to their content's own intrinsic width instead of filling the chat pane.
  Invisible for plain text (a narrow bubble still just looks like a normal
  chat bubble) but it starved chart cards of width. Fixed:
  `.msg.assistant .msg-content { flex: 1; min-width: 0; }`.
- **A ~42px phantom gap between a chart's `<canvas>` and its own wrapper**,
  caused by the canvas defaulting to an inline, baseline-aligned element
  before Chart.js's own `display:block` override takes effect. This
  silently pushed the Pin button down into the space the canvas visually
  painted over, making it unclickable — confirmed via direct DOM geometry
  inspection (canvas rect vs. wrapper rect had matching width/height but a
  different `top`). Fixed with the standard remedy:
  `.chart-wrapper { line-height: 0; overflow: hidden; }`.

### Data layout

```
data/
  mcp_servers.json          # MCP server registry
  llm_profiles.json         # LLM connection profiles
  dashboard.json.migrated   # pre-multi-dashboard flat file, kept for reference
  dashboards/
    <uuid>.json             # one file per dashboard
```

All gitignored and dockerignored (may contain internal URLs, API keys, or
query-result snippets) — same treatment `conversations/*.json` already had.

### Debugging notes worth keeping

- When a click handler mysteriously doesn't fire in a Playwright test but
  calling the same function via `page.evaluate()` works fine, check
  `document.elementFromPoint()` at the button's actual coordinates before
  assuming the JS is broken — it's very likely a CSS layout issue (another
  element visually covering the button), not a wiring issue.
- `.chart-type-btn` / `.conv-item` (etc.) selectors that exist in *both* the
  visible view and a `display:none` sibling view will resolve to the hidden
  one first in Playwright unless scoped with a parent id
  (`#dashboardGrid .chart-type-btn`, `#dashboardList .conv-item`, ...).
